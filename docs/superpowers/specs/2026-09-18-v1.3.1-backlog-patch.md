## 1. Goal

Land the 47 patch candidates raised by the post-release review of v1.3.0 as a single **behaviour-preserving** patch release.

"Behaviour-preserving" means, precisely:

* **No schema change that invalidates an existing model.** One new *optional* model field is added (`hub.kind`, section 6); every v1.3.0 model keeps validating and keeps rendering the same way.
* **No intentional geometry change.** The recipe is not being redesigned. Four items nevertheless move pixels as a side effect of fixing a measurement or a reserved-space bug - **A17**, **A23**, **A27**, **A28**. For those, the committed reference diagram is the arbiter: `tests/test_oci_layout.py::ExamplesTests::test_committed_reference_diagram_is_not_stale` compares `write_diagram(MODEL)` byte-for-byte against `OCI_Architecture.drawio`. If a fix changes those bytes, `OCI_Architecture.drawio` is regenerated in the same task and the README screenshots are regenerated once at the end of the release; if the bytes do not change, nothing is regenerated.
* **Two real defects are fixed** and each gets a regression test: **A22** (two unnamed DRGs abort the build) and **A43** (the parser invents DRG attachments the Terraform never declared).
* Roughly 40 of the 47 items are test-only, docstring-only or single-token work.

Everything else that the review raised - placement enrichments, team-guideline features, and the findings ruled "won't do" or already fixed - stays out (section 9).

## 2. Deliverables

1. The 47 items below, implemented in six batches plus a release task.
2. A regression test per bug fix, plus the ~20 coverage tests the review asked for.
3. `plugin.json` and every version string at `1.3.1`; a `[1.3.1]` CHANGELOG entry.
4. `OCI_Architecture.drawio` and the README screenshots regenerated **only if** the staleness test says they are stale.

## 4. Bug fix 1 - A22: two unnamed DRGs abort the build

### Current behaviour

`_layout_drg_column` derives the DRG's display name as:

```python
name = drg.get("name") or first_line(drg.get("label")) or "DRG"
addr = str(drg.get("address") or f"drg:{name}")
```

For the canonical label `"DRG\n<name>"` (the form the command, the skill and the parser all produce) `first_line` returns the literal `"DRG"`. Consequences for a DRG with no `name` and no `address`:

* the `drg_style="box"` group title is `"DRG: DRG"`;
* the registry alias is `drg:DRG`, so `{"source": "drg:prod-hub", ...}` cannot resolve;
* with **two** such DRGs the second `place_icons` call reuses the key `drg:DRG` and the build aborts with `ValueError: Duplicate cell key 'drg:DRG'`.

### Expected behaviour after the fix

Name resolution order, first non-empty wins:

1. `drg["name"]`.
2. The first non-blank line of `drg["label"]`, **unless** it is the bare word `DRG` (case-insensitive, punctuation-free).
3. The second non-blank line of `drg["label"]`.
4. `drg["address"]`.
5. `drg-<n>`, `n` being the 1-based position of the DRG in `model["drgs"]`.

The result is never the bare string `"DRG"`. `addr` keeps its existing definition (`drg["address"]`, else `drg:<name>`), so it is now unique whenever the labels or the positions differ.

Worked examples:

| model | name today | name after |
|---|---|---|
| `{"label": "Dynamic Routing\nGateway (DRG)"}` | `Dynamic Routing` | `Dynamic Routing` (unchanged) |
| `{"label": "DRG\nprod-hub"}` | `DRG` | `prod-hub` |
| `{"label": "DRG", "address": "drg-a"}` | `DRG` | `drg-a` |
| `{"label": "DRG"}` first in `drgs[]` | `DRG` | `drg-1` |
| two `{"label": "DRG"}` | `ValueError` | `drg-1`, `drg-2`; both render |

### Regression test

`tests/test_oci_layout.py`: build a model with two DRGs labelled `"DRG\nhub"` and `"DRG\nspoke"`, neither carrying `name` or `address`; assert the build no longer raises, that `d.layout_info["drg_style"]` has two distinct keys, and that `drg:hub` / `drg:spoke` resolve as edge endpoints. A second test covers the nothing-but-`"DRG"` case producing `drg-1` / `drg-2`.

## 5. Bug fix 2 - A43: the parser invents DRG attachments

### Current behaviour

`ModelBuilder._build_drg_links()` turns an IPSec connection, a **private** virtual circuit and a remote peering connection into a typed DRG attachment. When the DRG reference does not resolve it falls back to the tenancy's only DRG:

```python
drg = self.first_ref(r, attrs, DRG_TYPE)
if drg is not None:
    addr = drg.address
elif len(self.drg_by_addr) == 1:
    addr = next(iter(self.drg_by_addr))
else:
    continue
```

The fallback fires even when the resource declares **no** `drg_id` / `gateway_id` at all, so the model asserts connectivity the configuration never declares. The earlier fix wave applied exactly the opposite rule to `PUBLIC` virtual circuits: a resource that has no DRG reference is not an attachment, it stays an on-premises item with no connector.

### Expected behaviour after the fix

For each candidate resource, with `attrs` being `("drg_id",)` for IPSec and RPC and `("gateway_id",)` for a private virtual circuit:

1. **Explicit reference** - `first_ref(r, attrs, DRG_TYPE)` resolves a DRG in the configuration: attach to it. No warning. (Unchanged; this is what every fixture does.)
2. **Declared but unresolvable, DRG unambiguous** - the resource carries the attribute (`attr in r.attrs` or a non-empty `r.refs[attr]`, e.g. `drg_id = var.drg_ocid` or a reference to a DRG outside the parsed configuration) **and** the model holds exactly one DRG: attach to that DRG and record
   `WARNING: <address>: <attr> does not resolve; attaching to the only DRG <name>`.
3. **Declared but unresolvable, DRG ambiguous** - zero or 2+ DRGs: no attachment, record
   `WARNING: <address>: <attr> does not resolve and the model has <n> DRGs; no attachment`.
4. **Not declared at all** - the resource names no DRG: **no attachment**, record
   `WARNING: <address>: no <attr>; not attached to a DRG`.

Case 4 is the bug; today it lands in case 2's branch. The rule is the generalisation of the `PUBLIC` virtual-circuit rule: the parser never asserts a link the Terraform does not declare.

### Warning transport

`parse_terraform.py` has no warning channel today. Add one, deliberately small:

* `ModelBuilder.__init__` gains `self.warnings: List[str] = []`.
* `ModelBuilder.build()` copies them onto the model as `model["warnings"]` **only when the list is non-empty**, so every existing model dict is byte-identical to today's.
* `validate_model` accepts an optional `warnings` key (a list of strings) and rejects any other type.
* `summarise(model)` appends `, <n> warning(s)` when the key is present.
* `main()` prints each warning to stderr, prefixed as above, before the summary line.

### Regression test

`tests/test_parse_terraform.py`, from an inline HCL fixture in a temp dir holding one `oci_core_drg` and one `oci_core_ipsec` **without** `drg_id`: assert `model["drgs"][0]["attachments"] == []`, that `model["warnings"]` contains `no drg_id`, and that the IPSec resource still appears as a hub item. A companion test with `drg_id = var.drg_ocid` (declared, unresolvable, one DRG) asserts the attachment **is** created and a `does not resolve` warning is recorded. A third asserts the existing `hub_spoke` fixture is unchanged (four attachments, no warnings).

## 6. The `hub.kind` field (A03)

### Model

```python
"hub": {
  "kind": "onprem",          # optional: "onprem" (default) | "remote_region"
  "name": "On-premises",     # optional: overrides the title derived from kind
  "items": [...],
  "link_label": None,
}
```

* `kind` is **optional**; a missing or empty value means `"onprem"`, so every v1.3.0 model behaves exactly as before.
* `validate_model` checks `hub.kind` only when the key is present, and rejects anything outside `("onprem", "remote_region")`.

### Layout

`oci_layout.py` gains

```python
HUB_TITLES = {"onprem": "On-premises", "remote_region": "Remote region"}
```

and `_layout_hub` titles the panel `hub.get("name") or HUB_TITLES[kind]`. The container **keeps `group_type="onprem"`** in both cases - the styling (Neutral-1 fill, Neutral-3 border, left-aligned bold title) is the location-box style and is correct for a remote region too; only the title follows the kind. The hard-coded `"On-Premises"` default disappears, so a model with a hub and no name now reads `On-premises` (matching the parser's spelling) rather than `On-Premises`.

### Parser

`_build_hub()` already chooses the name; it now also sets the field:

```python
kind = "onprem" if onprem else "remote_region"
self.model["hub"] = {"kind": kind, "name": HUB_TITLES[kind], "items": self.hub_items, "link_label": None}
```

(the title table is imported from `oci_topology` so the parser and the layout cannot drift).

### Docs

* `SKILL.md` section 1 item 3: the panel label is `On-premises`, or `Remote region` when the hub holds only an RPC peer; `hub.kind` selects the default, `hub.name` overrides it.
* `SKILL.md` section 2 schema block: show `"kind": "onprem"` with its two values.
* `commands/drawio-architect.md` Step 2 item 7 and the Step 3 MODEL template: stop hard-coding `name = "On-premises"`; document `kind`.

## 7. Geometry, the reference sample and spec 7.2

* **A17**, **A23**, **A27**, **A28** can move pixels. **A23** is the most likely to move the committed reference (its DRG cluster has no left attachment box).
* The arbiter is `tests/test_oci_layout.py::ExamplesTests::test_committed_reference_diagram_is_not_stale`. Any task whose change makes that test fail regenerates `OCI_Architecture.drawio` with `examples/generate_reference_layout.py` **inside that task**, so every task ends with a green suite.
* The README screenshots (`screenshots/`, `Screens/`) are regenerated **once**, in the release task, and **only if** `OCI_Architecture.drawio` changed during tasks 1-6 (`examples/make_screenshots.py`, draw.io desktop required).
* **A28** settles an undocumented rule. Decision: the legacy region-level `"OCI Services"` panel (emitted only for a model with 2+ VCNs and top-level non-regional services) is **height-matched to the tallest VCN column**, exactly like the OSN panel, and keeps its position between the VCN columns and the OSN panel. Folding it into the OSN panel was rejected: the two panels mean different things (VCN-scoped services that no longer have a home VCN vs. regional services), and merging them would change which container an existing `services` edge endpoint resolves to. The topology-aware placement design spec section 7.2 gains one sentence recording the height rule and pointing at this document.

## 8. Testing strategy

* **Framework:** `unittest`, standard library only, discovered with `python3 -m unittest discover -s oci-drawio-architect/tests`. No new dependency.
* **TDD:** every behavioural item gets its failing test first. Test-only items (A06, A07, A10, A12, A15, A19, A20, A24, A26, A36, A39, A40, A45, A47) *are* the deliverable; each must be shown failing against the current code where it encodes a missing assertion that the current code would not satisfy, or, where it merely adds coverage of correct behaviour, run green immediately and be justified as coverage in the commit message.
* **Mandatory gates after every task:**
  * `python3 -m unittest discover -s oci-drawio-architect/tests` - all tests pass.
  * `python3 oci-drawio-architect/scripts/check_overlaps.py --strict OCI_Architecture.drawio` - exit 0.
* **Release gate (task 7):** the two above, plus `check_overlaps.py --strict` on a freshly generated demo, `scripts/smoke_test.sh`, and a `pack.sh` build into a temp directory.
* **Warning hygiene:** the new stderr warnings (A31, A32, A33, A43) must not appear when the reference model, the demo model or any committed fixture is processed. Each task asserting a warning captures stderr rather than letting it leak into test output.
