# Placement Enrichments (v1.4.0) - Design Specification

**Author:** Sergio Farfan
**Date:** 2026-09-18
**Plugin:** oci-drawio-architect 1.3.0 -> 1.4.0
**Repository:** `OCI-draw.io-Architect` (public, MIT), branch `feature/v1.4.0-placement-enrichments`
**Extends:** `docs/superpowers/specs/2026-09-17-topology-aware-placement-design.md` (v1.3.0) and
`docs/superpowers/specs/2026-09-17-security-constructs-addendum.md`. Model schema 2, the
`oci_layout.py` column order, `GROUP_TYPES`, the validator rules and the `ociGroup` / `ociRole`
style tokens defined there are used here unchanged unless a delta says otherwise.

## 1. Goal and scope

v1.3.0 made the layout topology-aware inside the region box. v1.4.0 closes the remaining gaps
between what Oracle's own figures draw and what the recipe emits, all of them about **where a
thing goes**, not about what a thing is:

- **Location boxes leave the region.** On-Premises, Internet and 3rd Party Cloud become
  page-level siblings of the OCI Region, the arrangement Oracle's Location Canvas defines. The
  hybrid connection label (Site-to-Site VPN / FastConnect / Remote Peering) moves into the gap
  between the two boxes, where Oracle puts it.
- **Gateways face what they connect to across that canvas.** The Internet Gateway and the NAT
  Gateway form one deterministic column on the border facing the Internet box, NAT below IGW;
  the Service Gateway faces the Oracle Services Network panel wherever the canvas puts it.
- **Compartments can become containers** of the VCNs they hold, with an optional tenancy
  wrapper - opt-in, because a view with every compartment drawn is unreadable.
- **Grouping boxes Oracle defines but never uses** (User Group, Tier) and one it does use
  (the OKE cluster box inside a subnet) become available to models that ask for them.
- **Subnet labels become two lines** - name on line 1 with a public/private token, CIDR on
  line 2. The two-line form is what Oracle's subnet grouping spec prescribes (slide 18); the
  public/private token is the plugin's addition, from the landing-zone figure and the team's
  guidelines (section 5).
- **Badges get legend rows**, the DRG gets its route-table badge, and the attachment connector
  style becomes a profile choice.

Non-goals: purpose selection, filtering, detail levels, the label-mode machinery, view layers, a
global-services bucket, participating-resource mode, multi-region canvases, AD/FD columns
(section 12). Everything stays standard-library Python 3.9+, deterministic (`key=` ids), and
gated by `check_overlaps.py`.

Backlog coverage: B01-B10 of the post-release triage, in the dependency order B07, B09, B10,
B08, B01 (ordering), **B03**, B02, B04, B01 (column), B06, B05.

Two evidence limits are recorded rather than papered over:
- The `.png` figure files for the NAT / service-gateway layouts are staged copies of the images
  embedded in the Networking docs pages; **no direct image URL exists**. They are cited by their
  docs page above and never by a made-up URL.
- **No corner radius is recorded for any Oracle grouping box** (sources give `rounded=1` /
  `roundRect` only). New rounded group types reuse the plugin's existing `arc_region` profile
  value rather than inventing one.
- **Oracle is not consistent about which side the Internet box takes.** The toolkit Location
  Canvas and every deck template put it on the **right** (with 3rd Party Cloud below it); the
  solutions-library reference architectures (`hub-and-spoke-drg`, `hub-spoke-oci`,
  `oci-core-landingzone`) put Internet on the **left**, next to on-premises, and consequently
  put the IGW on the VCN's left border. The plugin follows the toolkit canvas because that is
  the source that actually specifies a canvas; G1 and G4 are decisions taken on that basis, not
  a universal Oracle rule.

## 4. Design decisions (fixed)

Decisions **L1-L4** were taken by the author on 2026-09-18 and are not reopened here.
**G1-G10** are the consequences this spec settles.

- **L1. Location boxes outside the region are the default.** On-Premises, Internet and 3rd Party
  Cloud are drawn as **page-level siblings of the OCI Region** (deck slide 12, slide 7, toolkit
  Physical tile `toolkit_physical_r2c1`). The Site-to-Site VPN / FastConnect / Remote Peering
  label sits **in the gap between** the two boxes (slide 21). The IGW faces the Internet box
  (B02) and the IGW/NAT column (B01) follows from it. The v1.3.0 nested form is kept behind
  `locations: "nested"` / `--locations nested`.
- **L2. Compartments become containers around the VCNs they hold**, off by default, enabled by
  `show_compartments: true` / `--show-compartments`. Oracle has both patterns - the landing-zone
  figure nests `Tenancy (Root Compartment) > Enclosing Compartment > Network Compartment >`
  VCNs, slide 31 draws a compartment as an overlay crossing VCN boundaries - and the team's
  guidelines call compartments an optional per-view toggle. The container form is the one the
  plugin implements; the overlay form is not implemented (section 12). The tenancy grouping is
  designed only as far as B04 needs it: one `tenancy` container wrapping the compartment row.
- **L3. Attachment connectors stay thin solid, no arrowhead, by default**
  (`hub-and-spoke-drg` and the A-Team hub-and-spoke form). Dotted (the landing-zone form,
  and the team guidelines' "dotted = association") is an opt-in profile choice (B10). The badge
  and connector legend names whichever form is active.
- **L4. Label modes are a 1.5.0 feature with `Network` as the future default.** 1.4.0 ships
  B08 - the two-line subnet label, name on line 1 with a public/private token, CIDR on line 2 -
  as a **fixed form** consistent with that future default, without any mode machinery. Oracle's
  slide-18 Subnet spec fixes the two lines and their styling ("Top/Left, 9pt Bold Sienna;
  Text2: 9pt light Bark"), and the toolkit even allows a third role line
  (`Subnet A / 10.0.30.0/24 / Bastion Server`); the `(Public)` / `(Private)` token on line 1 is
  a plugin decision, not a toolkit form.
- **G1. Canvas order (landscape).** Left to right: **On-Premises** (narrow, full region height) |
  **OCI Region** | a narrow right column holding **Internet** on top and **3rd Party Cloud**
  below. Four independent *toolkit* sources agree with no contradiction among themselves
  (slide 12 rects, slides 24/27/29/31/32, toolkit tile `toolkit_physical_r2c1`, slide 27 point
  coordinates), and slide 7 makes the arrangement normative: "Location Grouping boxes are
  arranged in a specific way, shown on the Location Canvas slide." Outside the toolkit, Oracle's
  solutions-library reference architectures put the Internet box on the **left** instead (third
  evidence limit, section 2), so this is a **decision to follow the toolkit canvas**, not a
  universally observed rule. Unused boxes are dropped, which slide 12's Tip explicitly sanctions.
  Portrait is not implemented (section 12).
- **G2. Asymmetric gutters - a decision, supported by the *populated* templates only.** On
  slide 12's blank canvas both gutters are the same (~7 pt each side). They diverge as soon as a
  hybrid link is drawn: slide 27 has region-left minus on-prem-right = **68.2 pt** (~91 px)
  against internet-left minus region-right = **7.4 pt**, and toolkit Template 1 has **39 px**
  left against **10 px** right. The plugin adopts the populated form because the left gutter has
  to hold the Site-to-Site VPN / FastConnect label (G3): `LOC_GAP_LEFT = max(70, _hub_gutter(...))`
  and `LOC_GAP_RIGHT = 10`.
- **G3. The hybrid connection label sits at the midpoint of the gap segment**, in a
  backdrop-filled box, not at the midpoint of the whole edge (slide 21 plus all three toolkit
  examples). `_hub_gutter` already computes the width this needs; it is reused at page level.
- **G4. The Internet-facing border is the VCN's right border** under `locations: "outside"`,
  because the Internet box is the top box of the right column. The Oracle rule the evidence
  actually supports is *"the IGW and NAT straddle the VCN border on the side facing the Internet
  box"* - which side that is follows from where the Internet box was put: right in the
  Networking-docs service/NAT-gateway figures, **top-right** in `managingIGs.htm`, **top** on
  deck slide 31 and in the multi-region figure, **left** in `hub-and-spoke-drg`, `hub-spoke-oci`
  and the landing zone. Given G1 puts Internet on the right, the right border is the consequence.
  IGW and NAT form a vertical column there, **IGW above NAT**: that ordering is a **plugin
  decision**, not a finding - no Oracle source in the study fixes the vertical order, the toolkit
  draws no NAT at all, and the landing-zone figure stacks IGW / DRG-attachment / NAT with the
  attachment between them. Deck slide 31's top-border, caption-above form is reachable per
  gateway (`gateways[].side = "top"`) or per model (`gateway_edge: "top"`), and
  `gateway_edge: "bottom"` restores the 1.3.0 side choice. Whatever the side, the Internet-facing
  gateways are ordered **IGW, then NAT**, deterministically, not in model order (the B01 ordering
  half, which applies in every mode).
- **G5. The Oracle Services Network panel moves to a full-width band below the VCN stack**
  under `locations: "outside"`, and the Service Gateway moves to the VCN's **bottom** border
  facing it. **This is a decision, not a toolkit finding.** It is *required* for G4 to be
  drawable - with the OSN in the right column, every IGW/NAT connector would have to cross it -
  and the Service Gateway then follows Oracle's own invariant that the SGW sits on the VCN border
  facing the OSN (toolkit: right border when the OSN is right, bottom border when it is below).
  What the evidence does **not** support is that a below-the-VCN OSN is a *landscape* toolkit
  form: in every landscape deck slide and toolkit tile the OSN is a right-hand column matching
  the VCN's height, and the below-the-VCN strip appears only in the **portrait** template and
  portrait Example 2. It is, however, an Oracle form in the solutions library: the CIS landing
  zone puts the `Oracle Services Network` box at the **bottom**, below the compartment row, fed
  by every VCN's Service Gateway, and the multi-region full architecture puts the SGW on the app
  VCN's **bottom** border with the services drawn in region space below it. Those two figures,
  plus the drawability argument, are the basis. Under `locations: "nested"` the 1.3.0
  right-column OSN and right-border SGW are unchanged.
- **G6. One grouping mechanism, not three.** B05 (User Group, Tier) and B06 (OKE cluster) share
  one optional model field, `groups[]`, accepted on a VCN (bands around subnet rows) and on a
  subnet (a box around named items). No separate `oke_clusters[]` top-level list is introduced:
  an OKE cluster is a `subnet.groups[]` entry of type `oke_cluster`, which is where slide 32
  draws it. None of the three is ever emitted by default - no Oracle template uses a User Group
  or Tier box, and the OKE box needs a cluster-to-subnet mapping the parser can only sometimes
  produce.
- **G7. Compartment style follows slide 18 for the label colour.** The existing `compartment`
  container style keeps its dotted `dashPattern=1 1` (which matches the samples) but its label
  becomes **bold Sienna `#AE562C`** instead of Bark, per the slide-18 spec. This is visible only
  now that the container is drawn for the first time.
- **G8. An edge may terminate on a grouping box.** Slide 32 draws the load balancer connecting
  to the OKE cluster box, not to an icon inside it. `add_edge` already accepts a container id as
  an endpoint; the recipe resolves a `groups[]` entry's `key` as an edge endpoint.
- **G9. Validator rule 7 needs no change for compartments.** Verified in
  `drawio_builder.validate_registry`: rule 7 builds `network_groups` by filtering the container
  list to `gt in ("vcn", "subnet")` and iterates only over `leaves` (`kinds` in
  `("icon", "text", "other")`). Rule 7 tests **leaves** against
  containers whose `ociGroup` is `vcn` or `subnet`. A VCN inside a compartment is a container,
  not a leaf, so it is never tested; a leaf inside that VCN passes through the ancestor walk
  because the compartment is on its chain. The post-release triage's note that "rule 7 needs
  `compartment` added to the neutral list" is incorrect and is not implemented. What does change
  is rule 2 (container overlaps): compartment and tenancy containers must not overlap the DRG
  column, the OSN band or each other, which section 6.3's padding rules guarantee.
- **G10. Location boxes are siblings of the region, so nothing else in the validator moves.**
  Verified: rule 2 compares *any* two containers that are not in an ancestor relation and
  reports siblings explicitly (`where = "siblings" if pa == registry[b]["parent"]`), so the
  `LOC_GAP_LEFT` / `LOC_GAP_RIGHT` / `LOC_STACK_GAP` gaps of 6.2 are what keeps the four
  page-level boxes legal - any arithmetic that lets them touch is a hard `OVERLAP:` error. Rule 3
  measures a child against its own parent's `(0, 0, w, h)` box, which is unaffected by the
  parent's page position, so translating the region cannot break containment.
  They are not `vcn` or `subnet`, so rule 7 ignores them; their children are their own, so rule
  3 holds; `FOREIGN_TOL` and `STRADDLE_TOL` keep their v1.3.0 values and meanings. The only new
  geometric situation is an **edge crossing the region border** (on-prem item -> DRG, IGW ->
  Internet box): rule 6 counts crossings through icons and captions, which is unaffected by an
  edge passing over a container border.

## 5. Model schema delta

`schema_version` **stays 2**. Every field added below is optional and additive: a 1.3.0 model
parses, validates and lays out unchanged except for the two documented default flips (L1 and

accepted in the same list - every 1.3.0 value stays valid, so this is a superset, not a break,

  figure (`Web Subnet (Public)`) and the team's "make public versus private designation obvious",

### 6.2 The outer canvas (B03 / L1 / G1-G3)

`build_diagram` keeps building the region in region-local coordinates exactly as in 1.3.0, then
runs **one page-level pass** after `fit_to_children(rid)`. Nothing inside the region needs new
coordinate maths: the region container is simply translated, and `d.resize(rid, x=, y=)` moves
every descendant with it.

**Verified against the 1.3.0 builder (the B03 mechanism holds).** Child geometry in
`DrawioBuilder` is *parent-relative*: `_register()` stores each cell's own `x`/`y` as written,
and `_origin(cid)` walks the parent chain summing ancestor `x`/`y` to produce an absolute
position (`_abs_cell`, `abs_bbox`, `_abs_footprint`, `content_bbox` all go through it); the
emitted `mxGeometry` is likewise draw.io's parent-relative child geometry. `resize(cid, x=, y=)`
writes only that one cell's registry entry and its own `mxGeometry`, so translating the region
moves every descendant for free and no interior coordinate or id changes. Three constraints the
implementation must respect:
1. The pass must run **before** any page-level cell whose position is computed from the region's
   final box - which is why it sits after `fit_to_children(rid)` and before the SGW -> OSN edges,
   the notes text, the attachment edges, the model edges and the legend. In 1.3.0 the only cells
   emitted before that point are the title block, the region and the region's descendants; the
   only edges are the intra-hub links `_layout_hub` adds with `parent=hid`, and those carry no
   absolute geometry.
2. Edges are routed at `validate()` / `write()` time from cell ids, so a translation before
   routing is invisible to the router. An edge added with explicit `waypoints=` / pins *before*
   the pass would not move - the recipe must not do that.
3. `resize()` takes an **absolute new x**, not a delta, and does not re-centre children when only
   `h` grows (step 6).

```
phase order in build_diagram (new phases marked *)
  title
  region group (provisional)
* compartment / tenancy containers          <- 6.3, between the region and the VCN columns
  VCN columns (+ groups[] bands, 6.5; each VCN's own "OCI Services" panel is emitted
    inside _layout_vcn, and its edge gateways inside the same per-VCN loop iteration,
    sides from _gateway_sides, 6.4)
  region-level "OCI Services" panel for model-level services that stayed VCN-resident
  OSN panel  -> right column (nested) or full-width band below the stack (outside, G5)
  on-premises panel                          <- skipped when locations == "outside"
  DRG column (+ route-table badge, 6.6)
  fit_to_children(region)
* page-level location pass                   <- 6.2: translate the region, emit the sibling boxes
  SGW -> OSN edges
  notes, attachment edges, model edges
* legend (badge rows, 6.7)
  fit_page
```

The page-level pass, with `(rx, ry, rw, rh)` the region's fitted box:

1. `left_w  = LOC_W + LOC_GAP_LEFT` when a `hub` exists, else 0.
2. `right_w = LOC_W + LOC_GAP_RIGHT` when an Internet or 3rd Party box exists, else 0.
3. `d.resize(rid, x=rx + left_w)` - the region and everything in it shift right.
4. On-Premises at `(rx, ry, LOC_W, rh)`, `group_type="onprem"`, its items in one centred column
   with `HUB_PITCH`, vertically centred as `_layout_hub` already does.
5. Internet at `(rx + left_w + rw + LOC_GAP_RIGHT, ry, LOC_W, h_int)` and each 3rd Party box
   below it with `LOC_STACK_GAP`, the column's total height equal to `rh`
   (toolkit Template 1: 210 + 10 + 250 = 470 = the region's height). With one 3rd Party box the
   split is `h_int = round((rh - LOC_STACK_GAP) * 0.45)`, which reproduces the toolkit's
   210 / 250 (45.7%); slide 12 splits its column almost evenly instead (175.4 / 172.9), so 0.45
   is the toolkit's proportion, not a value both sources agree on. With no 3rd Party box,
   Internet takes the full `rh`.
6. Each box is floored at `LOC_MIN_H`; if the sum exceeds `rh`, the region is grown with
   `d.resize(rid, h=...)` rather than the boxes shrunk.

Hybrid connection labels (G3): the DRG attachment connectors that used to run inside the region
now cross its left border into the On-Premises box. They keep `kind="attachment"` and their
`Site-to-Site VPN` / `FastConnect` / `Remote Peering` label; the router's existing
label-placement search puts the text on the horizontal run, which is the gap segment, because
that is the only segment long enough. `LOC_GAP_LEFT` is sized from `_hub_gutter()` for exactly
this reason. The label box carries `labelBackgroundColor` from the page background so it masks
the line (slide 21).

### 6.3 Compartment containers (B04 / L2 / G7)

Inserted between the region and the VCN columns. Only VCNs participate; the DRG column, the
on-premises panel and the OSN band stay direct children of the region (the landing-zone figure
puts the DRG inside the Network Compartment, but the plugin's DRG column is shared by every
VCN and may serve VCNs in different compartments, so region level is the only correct parent).

- Membership: `compartments[]` object entries first, then `vcn["compartment"]` for any VCN not
  claimed; VCNs with no compartment go in a trailing unboxed group.
- Layout: compartments are laid out **in the VCN column order of their first member**, so the
  left-to-right order of the VCNs is preserved. Each compartment is a `compartment` container
  at `(cx, VCN_Y, ...)`; its VCNs are laid out inside it at compartment-local
  `x = CMP_PAD, y = CMP_TITLE_H`, then `fit_to_children(cid, pad=CMP_PAD)`.
- `_layout_vcn` and `_place_edge_gateway` take the **containing** cell id and coordinates in its
  space; their `region_id` parameter is renamed `parent_id` (both functions name it `region_id`
  today; `_place_edge_gateway` passes it straight to `place_icons` as the parent). A gateway therefore becomes a child
  of the compartment when its VCN is in one. `CMP_PAD = 30` is less than `GW_STRADDLE = 40`, so
  a bottom or side gateway's slot would poke out of the compartment; the fit call uses
  `min_h`/`min_w` grown by `GW_STRADDLE + PAD` on any side that carries a gateway, exactly as
  `_layout_vcn` already does for the VCN itself.
- Nesting: a compartment whose `parent` is another compartment is laid out inside it with the
  same padding. Depth is not limited; the landing-zone figure's two levels are the target.
- Tenancy: when `show_compartments` is on and `model["tenancy_name"]` is set, one `tenancy`
  container labelled `Tenancy: <name> (Root Compartment)` wraps the whole compartment row with
  `TEN_PAD` / `TEN_TITLE_H`. It is the hook the 1.5.0 global-services bucket will hang off; no
  other use is designed here.

### 6.4 Gateway sides (B01, B02 / G4, G5)

`_gateway_side(gw, vcn_index, order)` gains a `ctx` argument carrying `locations`,
`gateway_edge` and whether an Internet box exists, and a fourth return value `"top"`:

| Gateway | `locations: "outside"` (default) | `locations: "nested"` |
|---------|----------------------------------|------------------------|
| IGW | `right`, slot 0 | `bottom`, slot 0 |
| NAT | `right`, slot 1 (directly below the IGW) | `bottom`, slot 1 |
| SGW | `bottom` (faces the OSN band) | `right` (faces the OSN column) |
| LPG, peer in a later column | `right`, after IGW/NAT | `right`, after SGW |
| LPG, peer in an earlier column | `left` | `left` |
| LPG, peer unknown | `bottom`, after the SGW | `bottom`, after IGW/NAT |

`gateways[].side` overrides the row. `gateway_edge: "top"` moves the IGW and the NAT to the top
border, IGW in the **rightmost** slot (slide 31 puts it at the right end, nearest the Internet
box), NAT one `GW_PITCH` to its left, both with the caption **above** the glyph
(`add_icon(..., caption_above=True)`); the VCN gets `VCN_TOP_PAD_GW`. `gateway_edge: "bottom"`
restores the 1.3.0 side choice everywhere.

Within a side, gateways are sorted `igw, nat, sgw, lpg`, then by address - the B01 ordering
half, which applies in every mode and removes the model-order dependency.

Top-border slot geometry, VCN box `(vx, vy, vw, vh)` in its parent's space:
`x = vx + vw - TOP_GW_X0 - ICON_W - slot * GW_PITCH`, `y = vy - GW_STRADDLE + ICON_H` inverted
so the glyph centre lands on `vy`; with the caption above, the caption cell occupies
`y - LABEL_GAP - LABEL_H` to `y`, and `label_fill=COLORS["region_fill"]` masks the dashed
border as it already does on the other three sides.

### 6.5 `groups[]` boxes (B05, B06 / G6, G8)

A `subnet.groups[]` entry is laid out **after** the subnet's icons are placed and **before**
`_add_subnet_badges`, because the badges sit on the finished corner:

1. Resolve `items` to cell ids through `_Registry`.
2. Take their bounding box in subnet-local coordinates, inflate by `GRP_PAD` on the left, right
   and bottom and by `GRP_TITLE_H` on top.
3. `add_group(label, ..., parent=sid, group_type=<type>, key=<resolved key>)`, then re-run
   `fit_to_children(sid)` so the subnet grows around it.
4. Re-parent the enclosed icons to the group cell, so rule 3 and rule 7 see the true chain.

A `vcn.groups[]` entry does the same for whole subnet rows, parented to the VCN. Groups may not
overlap: two entries in the same container whose member sets interleave are a `ValueError`.

Slide 32's OKE box spans all three AD columns of its subnet. The plugin draws no AD columns
(section 12), so "spanning the ADs" reduces to "spanning the icon columns of its subnet", which
step 2 produces for free when the cluster and its node pools are the only items.

`_layout_drg_column` places the badge after the DRG icon, centred under its caption:
`cx = drg_slot_x + ICON_W / 2`, `cy = drg_slot_y + ICON_FOOTPRINT_H + DRG_RT_GAP + BADGE_SIZE / 2`,
parent = the DRG icon's parent (the region, or the `drg` group in box style), `host` = the DRG
icon id, key `<drg key>-rt`. The cluster height in `_drg_cluster_geometry` grows by
`DRG_RT_GAP + BADGE_SIZE` so the attachment stacks stay centred on the same axis. `add_badge`
already exempts a badge from rule 3 and from overlapping its host, so no validator change is
needed; the name goes in the tooltip and metadata, as the subnet badges do.

### 6.7 Legend (B07)

`add_legend` gains a third row kind, `("badge", <icon key>, text)`, rendering the glyph at
`LEGEND_BADGE_SIZE` centred at `(32, ry + row_h / 2)` - the same x centre as the group swatch -
with the text in the existing column at `x = 60`. Row height is unchanged at 22.

The recipe appends badge rows **only for the badge kinds actually present**, which it knows from
`_Registry`: route table, security list, NSG, and the DRG route table when B09 fired. It also
rewrites the attachment row's text to name the active form (L3): `Attachment (structural)` for
solid, `Attachment / association (structural)` for dotted.

## 8. Parser and tenancy changes

`scripts/parse_terraform.py` (`SCHEMA_VERSION` stays 2):

- **Compartments**: **no parser change.** `_build_compartments` already fills
  `model["compartments"]` with display names resolved through `compartment_names` from
  `oci_identity_compartment`, and `_compartment_name` already fills `vcn["compartment"]` through
  `new_vcn(..., compartment=)` - together that is exactly what B04's flat compartment row needs.
  `ModelBuilder` keeps `model["compartments"]` a list of **strings** (`ModelBuilder._finish()`,
  not `build()`, indexes `compartments[0]` to default the title's `compartment` field), so the
  object form of section 5
  stays a hand-written affordance; nested compartments (the landing-zone
  `Tenancy > Enclosing > Network` chain) are authored, not inferred. The parser does **not** set
  `show_compartments`; drawing them is a view choice.
- **Public flag**: no change needed. `infer_public(name, prohibit_public_ip_on_vnic)` already
  runs for every subnet and `new_subnet` always writes a bool, so B08 marks every parsed subnet.
- **OKE**: `oci_containerengine_cluster` already maps to the `oke` icon and
  `oci_containerengine_node_pool` to `vm`. New: when a cluster and at least one of its node
  pools land in the same subnet, emit one `subnet.groups[]` entry
  `{"type": "oke_cluster", "label": "<cluster display name>", "items": [cluster address, node
  pool addresses...], "key": "oke:<cluster name>"}`. Node pools that resolve to a different
  subnet are left alone - the box may only enclose members of its own subnet (section 6.5).
- **DRG route table**: `oci_core_drg_route_table` is added to the recognised resource set and,
  when it references a DRG, fills that DRG's `route_table` as `{"name", "address"}`. A DRG with
  several route tables takes the first by address order and records the rest in metadata; Oracle
  creates two by default (managingDRGs.htm) and drawing two badges under one glyph adds nothing.
- **User groups**: `oci_identity_group` is **not** mapped to a `user_group` box. An IAM group is
  a tenancy-level principal, not a network location; Oracle's own samples draw users as icons
  inside On-Premises or Internet, never in a User Group box. `user_group` stays available to
  hand-written models (B05's stated intent).
- **Tiers**: no new inference. `infer_tier` keeps feeding `subnet.tier` for row ordering; a
  `tier` grouping box is only ever explicit.
- **Internet box**: `ModelBuilder` emits `model["internet"] = {"name": "Internet", "items": []}`
  from `_finish()` when any VCN has an IGW, so the default canvas has something for the IGW to
  face. (`new_model()` must gain the key so `validate_model()` sees a stable shape.)
  `third_party` stays empty - Terraform gives no signal for it.
- `validate_model()` gains checks for `locations`, `gateway_edge`, `subnet_label`,
  `attachment_style`, `show_compartments`, the two `compartments` forms, `internet`,
  `third_party`, `drgs[].route_table` and `groups[]`. `summarise()` reports the compartment count
  and the group boxes.

`scripts/query_tenancy.py` - three corrections to the earlier draft, all verified against
`main`:

- `_REF_FIELDS` gains **`("drg_route_table_id", "drg_route_table_id")`**. Entries in
  `_REF_FIELDS` / `_SCALAR_FIELDS` are written in snake_case; `get()` matches the camelCase
  (`drgRouteTableId`) and kebab-case spellings through `_variants()`, so the snake_case entry is
  the correct one to add.
- **There is no `oci iam compartment list` call to piggyback on.** `fetch_live()` issues exactly
  three commands - `oci network vcn-topology get` (only with `--vcn-id`),
  `oci network networking-topology get` and `oci search resource structured-search` - and the
  tenancy name is fetched by `detect_settings.py`, not here. Compartment display names today come
  only from entities in that bundle typed `pt.COMPARTMENT_TYPE`, and `build_model()` names just
  the one compartment matching `--compartment-id`. Filling the section-5 compartment object form
  therefore means either mapping every `oci_identity_compartment` already in the bundle (no new
  call, but no parent chain - the search result keeps only `display_name`, `compartment_id`,
  `lifecycle_state`, `availability_domain`) or adding a fourth call,
  `oci iam compartment list --compartment-id-in-subtree true`. 1.4.0 takes the first, cheaper
  option; the parent chain stays authored.
- `oci ce cluster list` / `oci ce node-pool list` are likewise **new** calls, not existing ones;
  they feed the OKE grouping through the same `subnet.groups[]` shape. If the extra round-trips
  are unwanted, the OKE box simply is not emitted for live tenancies - it is opt-in either way.
- Live subnets carry `prohibit_public_ip_on_vnic` through `_SCALAR_FIELDS` **when the topology
  response supplies it**; `_search_items()` keeps only four scalar keys and drops it, so a
  search-only bundle falls back to `infer_public`'s name heuristic.

## 11. Migration and compatibility

- **Two visible default changes, both documented and both reversible in one key:**
  1. `locations` defaults to `"outside"` (L1). A 1.3.0 model renders with the on-premises panel
     outside the region, the OSN as a band below the VCNs, the SGW on the bottom border and the
     IGW/NAT on the right border. `locations: "nested"` (or `--locations nested`) restores the
     1.3.0 geometry **exactly**, which section 10's regression gate proves.
  2. `subnet_label` defaults to `"twoline"` (L4). `subnet_label: "inline"` restores the 1.3.0
     single-line form.
  Nothing else changes for an unmodified model: `show_compartments` is off, `groups[]` is empty,
  `attachment_style` is solid, and the badge legend rows only appear when badges do.
- **Schema**: still 2. Schema-1 models keep going through `migrate_legacy_model` unchanged.
  Parser output gains `internet` and, when present, `drgs[].route_table`, compartment objects
  and `subnet.groups[]`; consumers that compare whole model dicts must add them (none exist in
  the repository).
- **Cell ids**: unchanged for every existing element. The region keeps id `region`; location
  boxes take `hub` (as today), `internet` and `thirdparty:<n>`; compartments
  `compartment:<name>`; tenancy `tenancy`; group boxes `groups[].key` or the derived slug; the
  DRG badge `<drg key>-rt`. Because the region is *translated* rather than rebuilt, no interior
  coordinate and no interior id changes between the two canvas modes' shared parts.
- **Style output**: the `compartment` container's `fontColor` changes (G7) - visible only to
  hand-written diagrams that used `group_type="compartment"`, which the plugin never emitted.
  The `default`, `official` and `v1.0` profiles are otherwise byte-identical; `v1.0` keeps its
  guarantee.
- **Validator**: files written by 1.2.0 / 1.3.0 validate exactly as before (no rule changed).
- **CLI**: `--locations`, `--gateway-edge`, `--subnet-label`, `--attachment-style` and
  `--show-compartments` are added to `oci_layout.py`; every existing flag keeps its meaning.
- Generated scripts that call `write_diagram(MODEL, path)` need no change; those that want the
  old look add `locations="nested"`.

## 12. Out of scope

Deferred to 1.5.0 (the team-guideline feature set): diagram purpose selection; resource
filtering by tag / compartment / region / VCN / subnet / type / environment; cumulative detail
levels; the label-mode machinery and configurable caption fields (L4 ships only B08's fixed
form); draw.io view layers (`add_layer` remains built and unused); a global-services bucket
distinct from the OSN (the `tenancy` container of L2 is its designed host); all-resources versus
participating mode; relationship-discovery provenance.

Deferred with a stated reason:

- **Portrait canvas** (On-Premises band on top, Internet and 3rd Party side by side below,
  slides 25/28/30). The page-level pass of 6.2 is orientation-agnostic in principle but the
  DRG column, the hub gutter and the OSN band are all written for a horizontal axis.
- **Compartments as overlays** crossing VCN and subnet boundaries (slide 31). It is Oracle's
  other pattern, but an overlay is not a container, so it cannot use `add_group` and would need
  a z-ordered decoration primitive plus validator exemptions.
- **AD / FD columns** (`--show-ad-fd`). Slide 32's OKE box spans them; the plugin draws no AD
  columns, so 6.5 spans the icon columns instead.
- **Multi-region canvases** and cross-region Remote Peering between two region boxes; the
  `metro_or_realm` wrapper slide 19 defines for them.
- **A paperclip attachment glyph.** Oracle's docs figures use one; the bundled icon set does not
  contain it and Oracle's licence covers the toolkit icons only. The labelled rounded box stays.
- **The `oracle_services_network` Rose style.** Slide 19 assigns Rose `#A36472` to the
  "Optional" grouping and specifies 2pt dashed Neutral 3 for the OSN; the samples draw it
  Sienna. The v1.3.0 decision to keep Rose with a provenance note stands - changing it would
  churn every screenshot for a style question this release does not otherwise touch.
- **Two DRG route-table badges** for the two default route tables Oracle creates.

## 13. Open questions

Four choices are recorded for transparency, all decided; five questions raised by the design
review of 2026-09-18 are open but **non-blocking** (each has a stated fallback).

Decided:

1. **Why the OSN moves (G5) rather than the IGW.** With the Internet box in the right column and
   the OSN in the right-hand column inside the region, every IGW and NAT connector would have to
   cross the OSN panel. Moving the OSN to a full-width band below the VCN stack is the only
   arrangement that keeps both Oracle placements legal, and it is itself an Oracle form
   (slide 30, toolkit tile `toolkit_physical_r4c1`). The alternative - IGW on the top border per
   slide 31 - is kept as `gateway_edge: "top"`, not as the default, because the deck shows it
   once and the Networking docs figures show the right-border column three times, and because it
   is the only one of the two that also places the NAT.
2. **Why no `oke_clusters[]` top-level list (G6).** Slide 32 draws the cluster box inside a
   subnet, so the subnet is its natural owner; one `groups[]` field covers B05 and B06 and keeps
   the OKE case from needing its own layout pass.
3. **Why `oci_identity_group` does not become a User Group box (section 8).** An IAM group is a
   tenancy principal, not a location; Oracle's samples draw users as icons inside On-Premises or
   Internet. The box stays available to hand-written models, which is all B05 asked for.
4. **Why validator rule 7 is unchanged (G9).** The post-release triage expected compartments to
   need an exemption. They do not: rule 7 tests leaves against `vcn` and `subnet` containers
   only, and a VCN is a container. The note is corrected rather than implemented.

Open (raised by the design review; none blocks implementation):

5. **Does the CPE straddle the On-Premises border?** Oracle is unambiguous - the toolkit centres
   the CPE icon exactly on the On-Premises box's region-facing border in all four samples
   (Template 1 CPE centre `x=-690` = On-Premises right edge `-690`), mirroring the DRG on the
   VCN border. 6.2 step 4 keeps the 1.3.0 behaviour of a centred interior column, which is a
   *deviation*. Fallback: leave it; the builder already supports it (`add_icon(label_fill=)` +
   the rule-3 straddle tolerance), so it can be a one-line change in 1.4.1 if the sample looks
   wrong.
6. **Should the region grow, or the location column shrink, when the right column does not
   fit?** 6.2 step 6 grows the region (`d.resize(rid, h=...)`). That leaves the region's children
   top-aligned in a taller box rather than re-centred, so the DRG column and the on-premises
   panel - both centred on the VCN stack at build time - stop being centred on the *region*.
   Fallback: accept it (Oracle's Template 1 also top-aligns), or re-run the DRG/hub centring
   after the grow.
7. **Is the OKE box's `GRP_TITLE_H = 30` enough clearance from the subnet's own title?** The
   subnet title occupies `ROW1_Y = 50` and the group box is inflated upward by 30 from the icon
   bounding box, whose top is already at `ROW1_Y`; the group's own title band therefore starts at
   `y = 20`, inside the subnet's title strip. Fallback: raise the subnet's `ROW1_Y` when it holds
   a `groups[]` entry, or push the group's contents down. A validator rule-4 caption collision
   would catch it in the tests either way.
8. **Two DRG route tables, one badge.** Oracle creates one route table for VCN attachments and
   one for everything else (`managingDRGs.htm`); section 8 takes the first by address order and
   puts the rest in metadata, and section 12 defers a second badge. If a hub-and-spoke diagram
   routinely needs both, the badge should become a 2-glyph strip rather than a single icon.
9. **Where does the `groups[]` cell sit in the routing lattice?** 6.5 re-parents the enclosed
   icons to the group cell, which makes the group a container the lattice router must dock
   around (G8 wants edges to *terminate* on it). This has no 1.3.0 precedent - every container
   the router has met so far is a region / VCN / subnet / services panel. Fallback: the mandatory
   `check_overlaps.py` gate plus the rule-6 crossing warning will expose it in the demo page 3
   test before release.
